# ۲) Coordinator — چطور سه منبع یادگیری بدون ناپایدارسازی مدل ترکیب می‌شوند

این مهم‌ترین بخش فنی پروژه است. کد: [`src/coordinator.cpp`](../src/coordinator.cpp).

## ۲.۰ صورت مسئله

سه ترد هم‌زمان یاد می‌گیرند و هر سه می‌خواهند **همان** وزن‌ها را عوض کنند. اگر ساده‌لوحانه
هر کدام روی وزن مشترک `θ` گرادیان بزنند، سه اتفاق بد می‌افتد:

1. **race condition** روی حافظه‌ی وزن‌ها (نتیجه: وزنِ نیم‌آپدیت‌شده، NaN).
2. **destructive interference**: `Δθ₁` و `Δθ₂` می‌توانند تقریباً قرینه باشند؛ جمعشان مدل را
   به جایی می‌برد که هیچ‌کدام نمی‌خواستند (و loss هر دو بدتر می‌شود).
3. **model collapse**: ترد داده‌ی خودتولید، خروجی خودش را یاد می‌گیرد → توزیع باریک‌تر →
   خروجی تکراری‌تر → حلقه‌ی بازخورد مثبت تا فروپاشی.

راه‌حل این پروژه: **هیچ تردی روی وزن زنده نمی‌نویسد.** هر ترد یک *پیشنهاد* می‌سازد و
coordinator تنها نویسنده است.

```
Δθᵢ = θ_local(بعد از آموزش محلی) − θ_base(همان لحظه‌ای که sync کرد)
```

`Δθᵢ` یک وکتور flat روی *فضای ادغام* است: اجتماع پارامترهای trainable هر سه ترد
(`FlatSpec` در `core/params.h`). چیزی که ترد آموزش نداده، در آن مختصات صفر است.

## ۲.۱ خط لوله‌ی ادغام (۶ مرحله)

### مرحله ۱ — میرایی فیشر (EWC سبک)

یک تخمین قطری از ماتریس اطلاعات فیشر روی **holdout** نگه می‌داریم:

```
F ← (1−ρ)·F + ρ·g²        g = ∇θ  L_holdout ,  ρ = coord.fisher_ema
```

سپس هر پیشنهاد را در جهت پارامترهای «مهم» کم‌اثر می‌کنیم:

```
Δᵢ[j] ← Δᵢ[j] / ( 1 + λ · F[j]/mean(F) )        λ = coord.fisher_lambda
```

این همان ایده‌ی Elastic Weight Consolidation است، اما به‌جای اضافه‌کردن جریمه به loss
(که نیازمند تغییر تابع هدف هر سه ترد بود) به‌صورت **پیش‌شرط‌گذار (preconditioner)** روی
آپدیت اعمال می‌شود: پارامترهایی که برای وظیفه‌ی اصلی حیاتی‌اند سخت‌تر حرکت می‌کنند.
نتیجه: فراموشی فاجعه‌بار به‌شکل ساختاری مهار می‌شود، نه با امید.

### مرحله ۲ — ناحیه‌ی اعتماد به‌ازای هر منبع

```
اگر ‖Δᵢ‖ > ρᵢ·‖θ‖   →   Δᵢ ← Δᵢ · ρᵢ‖θ‖ / ‖Δᵢ‖         ρᵢ = coord.trust_ratio
```

یعنی هیچ منبعی — مهم نیست چند قدم زد یا چقدر داده‌اش بد بود — نمی‌تواند مدل را بیش از یک
نسبت مشخص جابه‌جا کند. در تست عملی با `lr=0.03` (۱۰۰۰ برابر بزرگ‌تر از حالت عادی) نُرم خام
پیشنهاد `46.5` بود و همین مرحله آن را به `0.43` محدود کرد.

### مرحله ۳ — تراش TIES

فقط `coord.ties_keep` درصد بالای مختصات هر پیشنهاد (بر اساس قدر مطلق) نگه داشته می‌شود و
بقیه صفر می‌شوند:

```
thresh = k-امین بزرگ‌ترین |Δᵢ| ,  k = ties_keep·N
Δᵢ[j] ← 0   اگر |Δᵢ[j]| < thresh
```

مختصات کوچک عمدتاً نوفه‌ی SGD هستند و بیشترین سهم را در تداخل بین منابع دارند
(این نتیجه‌ی مقاله‌ی TIES-Merging است). تراش‌کردن آن‌ها هم تداخل را کم می‌کند و هم
sparsity می‌دهد.

### مرحله ۴ — تصویرسازی PCGrad

برای هر جفت متعارض (`cos < 0`) مؤلفه‌ی متضاد را حذف می‌کنیم:

```
اگر ⟨Δᵢ, Δⱼ⟩ < 0 :   Δᵢ ← Δᵢ − (⟨Δᵢ,Δⱼ⟩ / ‖Δⱼ‖²) · Δⱼ
```

بعد از این مرحله هیچ جفتی فعالانه یکدیگر را خنثی نمی‌کند: هر پیشنهاد فقط مؤلفه‌ی
«غیرمخرب» خودش را نگه می‌دارد. تعداد تصویرسازی‌های انجام‌شده در هر دور در audit log
ثبت می‌شود (`projections=…`) و ماتریس شباهت کسینوسی سه‌گانه در GUI زنده دیده می‌شود
(سبز = هم‌راستا، قرمز = متعارض).

### مرحله ۵ — انتخاب علامت + میانگین وزنی

وزن هر منبع:

```
wᵢ = priority(source) × credit(source)
```

- `priority` ثابت و قابل‌تنظیم است (پیش‌فرض: feedback 1.4 > continual 1.0 > selfgen 0.6).
- `credit` یک امتیاز یادگیرنده (bandit) است: منبعی که پیشنهادهایش پذیرفته می‌شود و
  هم‌راستا با جهت پذیرفته‌شده است اعتبار می‌گیرد، منبعی که رد می‌شود اعتبارش ضرب در ۰.۸ می‌شود.

  ```
  align = cos(Δᵢ, Δ_merged)
  accept:  creditᵢ ← clamp( creditᵢ·(1+0.10·align) + 2·(L_before−L_after)·max(0,align), 0.05, 2.5 )
  reject:  creditᵢ ← max(0.05, creditᵢ·0.8)
  ```

  این یعنی سیستم خودش یاد می‌گیرد به کدام منبع بیشتر اعتماد کند — بدون تنظیم دستی.

ادغام نهایی به سبک TIES (انتخاب علامت، بعد میانگین فقط روی موافق‌ها):

```
s      = sign( Σᵢ wᵢ·Δᵢ[j] )
Δ[j]   = ( Σ_{i: sign(Δᵢ[j])=s} wᵢ·Δᵢ[j] ) / ( Σ_{i: sign(Δᵢ[j])=s} wᵢ )
```

اگر دو منبع در یک مختصات علامت مخالف داشته باشند، *فقط* برنده‌ی وزنی می‌ماند؛ میانگین‌گیری
ساده در چنین حالتی هر دو را تضعیف می‌کند (همان چیزی که «تداخل مخرب» می‌نامیم).

### مرحله ۶ — ناحیه‌ی اعتماد کل + محدودکننده‌ی نرخ

```
‖Δ‖ ≤ global_trust_ratio · ‖θ‖
```

و یک **token bucket** روی «نرخ تغییر مدل در دقیقه»:

```
bucket ← min(rate_burst, bucket + Δt/60 · rate_per_minute)
نیاز    = α·‖Δ‖/‖θ‖
اگر نیاز > bucket → Δ مقیاس می‌شود تا در بودجه جا شود
پذیرش  → bucket -= نیاز
```

این مستقیم‌ترین دفاع در برابر model collapse است: حتی اگر همه‌ی گیت‌ها فریب بخورند،
سرعت رانش مدل سقف دارد و انسان فرصت دیدن و مداخله دارد.

## ۲.۲ اعمال محتاطانه: line-search + گیت holdout

```
برای α در {1, 0.5, 0.25}:
    cand = θ + α·Δ
    اگر drift(cand) = ‖cand − anchor‖/‖anchor‖ > anchor_drift_max  →  α بعدی
    (loss, entropy) = eval(cand)  روی holdout ثابت
    gate = min( L_before + accept_tolerance ,  L_best + regression_budget )
    اگر loss ≤ gate  و  entropy ≥ entropy_floor_ratio · entropy_baseline:
        publish(cand);  break
رد شد → هیچ تغییری اعمال نمی‌شود (rollback خودکار)
```

چهار نکته‌ی مهم:

1. **گیت دوطرفه (ratchet)**: تنها `L_before + tolerance` کافی نیست. در آزمایش واقعی دیدیم
   که با تلورانس ۰.۰۰۳ مدل هر دور «فقط ۰.۰۰۲ بدتر» می‌شد و بعد از ۱۸ دور از ۱.۱۷۵ به
   ۱.۲۱۱ رانده شده بود، در حالی که همه‌ی دورها «پذیرفته» بودند. با اضافه‌کردن
   `min(..., L_best + regression_budget)` این رانش بسته شد و رد‌شدن‌ها ظاهر شدند:

   ```
   auto-rollback, rejected: holdout regression 1.1864 -> 1.1869 > gate 1.1866
   ```

2. **گیت آنتروپی**: صرفاً loss کافی نیست. فروپاشی خودآموزی معمولاً اول به‌شکل *باریک‌شدن
   توزیع* ظاهر می‌شود (تکرار، حرف‌های قالبی) و ممکن است loss را حتی کمی بهتر کند. پس
   میانگین آنتروپی پیش‌بینی روی holdout هم اندازه‌گیری می‌شود و اگر زیر ۷۵٪ خط پایه‌ی
   جلسه بیفتد، آپدیت رد می‌شود.

3. **anchor**: یک میانگین متحرک نمایی از وزن‌ها (`anchor_ema`) نگه داشته می‌شود و رانش
   نسبت به آن سقف دارد. anchor نقش «حافظه‌ی بلندمدت» را بازی می‌کند: هر دور می‌تواند کوچک
   باشد، اما مجموع دورها نمی‌تواند مدل را از anchor دور کند.

4. **rollback ذاتاً امن است**: نامزد همیشه یک `ParamStore` *جدید* است و انتشار = تعویض
   اتمیک اشاره‌گر. پس «برگشت» یعنی صرفاً منتشر نکردن؛ هیچ حالت نیمه‌آپدیت‌شده‌ای وجود ندارد.
   علاوه بر آن بهترین snapshot جلسه نگه داشته می‌شود و دکمه‌ی `restore best` (یا کلید `b`
   در داشبورد ترمینالی) هر وقت لازم شد به آن برمی‌گردد. هر N دور یک checkpoint fp16 روی
   دیسک نوشته می‌شود و نسخه‌های قدیمی چرخشی پاک می‌شوند.

## ۲.۳ پنجره‌ی ادغام: چرا لازم شد

در نسخه‌ی اول، coordinator به‌محض رسیدن هر پیشنهاد آن را پردازش می‌کرد. نتیجه: عملاً هیچ‌وقت
دو پیشنهاد هم‌زمان نبودند، پس همه‌ی مکانیزم حل تعارض بی‌کار می‌ماند و رفتار سیستم به
«آپدیت‌های متوالی» تنزل می‌کرد (در لاگ‌ها: `cos(CL,SG) +0.00`).

راه‌حل: `coord.merge_window_s`. با رسیدن اولین پیشنهاد، coordinator تا این مدت (یا تا رسیدن
پیشنهاد از همه‌ی تردهای فعال) صبر می‌کند. بعد از این تغییر، ادغام واقعی سه‌منبعی رخ می‌دهد:

```
cos(CL,SG) +0.05  cos(CL,FB) +0.05  cos(SG,FB) +0.07
```

پیشنهادهای کهنه (پس از انتشار نسخه‌ی جدید) حذف نمی‌شوند بلکه میرا می‌شوند:
`stale = 1/(1 + version_now − version_base)` — همان ایده‌ی تصحیح staleness در SGD نامتقارن.

## ۲.۵ گزینه‌های دیگر و دلیل انتخاب

| گزینه | چرا انتخاب نشد |
|---|---|
| میانگین‌گیری ساده‌ی وزن‌ها (model soup) | در تعارض علامت، هر دو منبع را تضعیف می‌کند؛ هیچ گیت کیفیتی ندارد |
| اجرای متوالی با قفل انحصاری روی وزن | ترد کند همه را بلاک می‌کند؛ آخرین نویسنده برنده می‌شود؛ تداخل حل نمی‌شود |
| جمع کردن گرادیان‌ها در یک بهینه‌ساز مشترک | نیازمند هم‌زمانی گام‌ها و بچ‌های هم‌اندازه است؛ سه منبع نرخ‌های خیلی متفاوت دارند |
| EWC کلاسیک (جریمه در loss) | باید تابع هدف هر سه ترد را تغییر دهد؛ به‌شکل preconditioner در coordinator تمیزتر و متمرکزتر است |
| PPO برای بازخورد | reward model + value head + rollout؛ برای مدل ۱۰M و چند ده امتیاز ناپایدار است → DPO انتخاب شد ([جزئیات](STEP_BY_STEP.fa.md#ج-ترد-بازخورد-dpo)) |
